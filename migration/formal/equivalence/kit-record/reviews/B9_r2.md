## Verdict

**No difference found.** Four new samples, 294 cases, 4,131 compared values (3,787 result values
+ 344 values that guard the typed input), 0 differences, localisation mask 0 on every sample. No
DEFECT. Two NOTEs (one is a candidate PRECOND for the orchestrator), both on the sample whose final
model is the intercept alone.

## Method

Generator: `migration/diffeval/units/b9_r2_gen.py`. It imports the implementer's `b9_gen.py`
unchanged (recorders on the real `train.run`, the real `StepwiseResult` as a literal, table lambdas
for `chi2` / `pow2` / `log1p`, digest-keyed lambdas for `solve` / `matmul` / `matvec` / `dot` / `inv`
/ `einsum_q`, the injective encoding of the five formatters cross-checked in Python against the
real formatters, the compact table encoding) and changes only the data:

- the full feature files come from the real `feature_engineering.run` on `data/cs-training.csv`
  with `inputs/split_ids.csv`, written to a temp dir outside the workspace;
- rows are drawn with `numpy.random.default_rng(seed)`, with a chosen number of events, in random
  row order (the implementer's sample was a stride in file order);
- nulls are planted in candidate columns that the stepwise fit selects, in `default_flag` and in a
  non-candidate column (`age_group`), in both files;
- two cases were added to every suite: the digests of the two input frames as Lean decoded them
  (43 values each). They guard the typed `eval_decl` input (the tables are 16–22k characters).

Per sample, ONE `eval_decl(def:zz_carrier, zz_carrier)` input. Inside Lean the fifteen steps are
chained on the Lean results of the earlier steps and each result is compared with the locals of
the real run; then the whole `run_py_py_py` is compared with the 18 frames captured at
`write_sas_csv` (file name, order, rows, columns, every column: name and cells as bits or
strings) and with `model.json` (`intercept`, `coefficients` in dict order).

Typed input: for sample B the tool saved its reply to a file, and the input the server echoed is
byte-identical to the generated one (52,963 characters). For A, C, D the input guard cases pass,
the `StepwiseStep` read-back passes and the mask is 0.

Seeds: 58 real `train.run` runs were made to choose the samples (A config: seeds 1–6; B config:
1–25; null config, two plantings: 1–12 and 1–14; D: 1). 8 of them raised
`RuntimeError: stepwise_logistic: the fit at step k did not converge` (A: seed 5; B: 2, 10, 25;
null configs: 1 and 9, twice) and were not usable.

## Findings

**NOTE 1 (candidate PRECOND; RULEBOOK §2.6, §6 "zero-row tables", amendment B2).** Sample D,
`train.py:335-339`. With a final model that has no effect, Python builds
`pl.DataFrame({"Effect": [], "OddsRatioEst": [], "LowerCL": [], "UpperCL": []})` (0 rows, 4
columns) and `write_sas_csv` writes the header line `Effect,OddsRatioEst,LowerCL,UpperCL`. The Lean
returns `("printed_odds_ratios.csv", [])`: the table with no row, which carries no column name. The
harness compares only "rows = 0" there, so the case passes. The rulebook records zero-row tables
as a limit and §2.6 requires the *input* tables to be non-empty; nothing requires
`final_effects ≠ []`. The preconditions I read (`run_py_py_py_precond`, steps 01, 03, 04, 06, 10)
do not exclude this input. I did not establish whether `hosmer_lemeshow_precond`,
`classification_table_precond` or `association_table_precond` (reached through steps 05, 07, 08)
exclude it; they are `Prop`s and were not evaluated. If they do not, the limit is reached by an
output on an input the precondition allows and deserves a `-- narrowing:` line or a recorded limit
for outputs.

**NOTE 2 (RULEBOOK §2.3, frame literal "with the dtype the constructor produces").** Same input,
`def:train_run_06_coefficients_odds`. The frame `printed_odds_ratios` is built as four
`Pl.Col.str []` columns; polars gives four Null-dtype columns of height 0
(`Schema({'Effect': Null, …})`). Not observable in the result: `Pl.toTable` of a zero-height frame
is `[]` either way, and the frame is not returned.

## What this test does not show

- The five formatters are an injective encoding of their arguments on both sides: a cell is equal
  exactly when the formatter received the same arguments. The real strings are checked in Python
  only (`b9_gen.check_real_against_encoded`: every formatted cell of the run with the real
  formatters is the real formatter applied to the decoded arguments; 762 / 835 / 693 / 114 cells
  for A / B / C / D, no assertion failed).
- The library routines return numpy's results when the digest of the arguments' bits is what numpy
  received. A wrong argument would give an empty array or the sentinel and show as a difference;
  none did. The routines themselves are outside the model.
- Integer counts that reach `fmt_wd` as Python ints are encoded as `float(v)` (R-F2I).
- Membership of the samples in the full precondition was not evaluated (see NOTE 1).
- No sample makes a validation `predicted_logit` overflow `exp` (not required).
