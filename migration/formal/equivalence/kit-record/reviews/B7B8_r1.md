## Findings

### F1. PRECOND: join suffix clash is not excluded (both bundles)

Source: feature_engineering.py:94-96, predict.py:99-101 (`join(..., on="age_group", how="left")`).
polars renames a right column whose name exists on the left to `<name>_right`, and raises
`DuplicateError` if that name exists too. No conjunct of the four preconditions mentions it.

B7. Input (imported frame, all Float64, 2 rows): the 12 standard columns with
`VAR1=[1,2]`, `age=[45,46]`, `MonthlyIncome=[3000,null]`, `NumberOfDependents=[1,1]`, plus
`median_income=[11,11]` and `median_income_right=[22,22]`; split `row_id=[1]`; `input_best32` the
identity (Float64 in, Float64 out, so the conjunct on `input_best32` holds).
- Python (real `run`, `proc_import_csv` replaced by the frame): `DuplicateError: column with name
  'median_income_right' already exists`. Same through a real CSV with the two extra columns.
- Lean `run true IB T S false false`: 2 tables, 1 row of 42 cells each; `monthly_income` is 3000.0
  in the train row and 11.0 (the left frame's own `median_income`) in the validation row.
- Every conjunct of `run_precond` holds: names distinct, numeric columns present, step
  preconditions hold on the Lean intermediates.

B8. Same table as `cs_test` (with `SeriousDlqin2yrs` null), `intercept=0.1`,
`coefficients=[("age", 0.01)]`, `medians=none`, flag off.
- Python: `DuplicateError: column with name 'median_income_right' already exists`.
- Lean `run_py_py`: 2 tables (2 rows x 2 cells, 2 rows x 15 cells), `monthly_income` 3000.0 and 11.0.

B8, second way in (flag on): a medians file with columns `age_group, median_income, age, age_right`
covering 1..5. Python: `DuplicateError: column 'age_right' is duplicate`.
`predict_run_02_medians_precond` and `predict_run_04_imputed_precond` hold (not evaluated in Lean;
no conjunct constrains the other columns of the medians frame).

Needed: for every right column `c` other than the key that is also a left column, `c ++ "_right"`
is neither a left column nor a right column.

### F2. PRECOND: `run_precond` admits a text `median_income` column in cs-training

Source: feature_engineering.py:100-103, then :157.
Input: as F1/B7 but with one extra column `median_income = ["abc","abc"]` (text) and no
`median_income_right`.
- Python: `InvalidOperationError: division with 'String' datatypes is not allowed` (at :157; the
  `when/then` of :100-103 took the left frame's String column and gave a String `monthly_income`).
- Lean: `fe_run_04_imputed` gives `monthly_income` as Float64 `[3000.0, null]`, so
  `fe_run_05_features_precond` (Float64 `monthly_income`) holds on the Lean intermediate and
  `run_precond` holds as a whole. `run` then returns tables.

B8 is not affected: `predict_run_04_imputed_precond` states the kind of `median_income` on the
joined frame (`f64 (test_cleaned.join ...) "median_income"`), which is false here. Python
`predict.run` raises the same error on that input, and the precondition excludes it. B7 states it
on `income_medians` only, which is not the column the select reads when the left frame has one.

### F4. RULE (form only): `full` on reductions with fewer than 5 operands

RULEBOOK §2.3: "a horizontal reduction with exactly 2 operands (or `sum_horizontal` with at most 4):
pass the literal `true`".
- `def:fe_run_05_features` passes the unit's `full` to the 3-operand `sas_sum` (:130), to `sas_max`
  (:193) and to both `sas_min` (:211, :214).
- `def:predict_run_05_features` passes `true` at the same four sites (:126, :198, :211, :212) and
  `full` only to the 5-operand `sas_sum` (:191), as §2.3 says.

The value cannot differ. Evaluated on `Pl.sumHorizontal` directly, with rows where association
changes the result (1e16, 1, 1 / 1, 1, 1e16): `full = true` and `false` agree for 3 operands (both
orders) and for 4, and disagree for 5 (so the probe discriminates); `maxHorizontal` and
`minHorizontal` with 2 operands agree. `fe_run_05_features true` and `false` also give the same
digest on both my inputs. Form inconsistency between the two implementers, nothing else.

### F5. RULE (form): position of the parameter that is both a Python parameter and a §3 parameter

§3: explicit parameters are "placed before the Python parameters, in the order listed".
- `def:run`: `(full) (input_best32) (cs_training split_ids) (fix_income_truncation export_train_medians)`.
  `split_ids` (a §3 row) sits in its Python position, after `cs_training`.
- `def:run_py_py`: `(full) (input_best32) (intercept) (coefficients) (medians) (cs_test) (fix_train_medians)`.
  `medians` (a §3 row, and the last Python parameter) sits with the explicit parameters.
- `def:fe_run_06_split` puts `split_ids` first, i.e. the B8 reading.

One of the two runs deviates, depending on the reading; the rulebook does not settle it. Candidate
for an amendment.

### F8. NOTE: zero-row output tables

Python writes a header-only file when no row is selected (`model_features_train.csv`: 0 x 42 with
a split file naming no row of the frame) and for `income_medians.csv` when there is no income at
all with `export_train_medians` (0 x 2). `run_precond` allows both. By §2.6 a zero-row table is
`[]` and carries no column names, so the Lean result cannot hold those headers. This is the
recorded limit "zero-row tables" (§6); the rulebook requires non-empty input tables only. Not
evaluated: the harness digest of an empty table is the same on both sides.
