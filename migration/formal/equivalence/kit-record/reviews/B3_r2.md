## Findings

### D1 — DEFECT — `proc_rank_apply_groups` differs from Python for k < 0 (precondition allows it)

Source: sas_compat.py:626-630. `starts` is sorted on `g`; `np.searchsorted(lo, xv, side="right")`
is a binary search that is only meaningful when `lo` is ascending. For k < 0 the group number
decreases with the rank, so after `.sort("g")` the array `lo` is DESCENDING and numpy's binary
search returns what it returns on an unsorted array. The Lean uses `Np.searchsortedRight lo t`,
which is the count of elements `<= t` (prelude comment: "Every call site passes a sorted array";
RULEBOOK §6 `searchsorted*`), and the unit's comment asserts "lo is sorted (group starts increase
with the group number)". That is false for k < 0, and `def:proc_rank_apply_groups_precond` does not
require `0 <= k` (it only asks Float64 columns, a non-null reference value and group values in the
Int64 range).

Minimal input (precondition holds: groups are -1, -2):
`reference = [1.0, 2.0, 3.0, 4.0]`, `x = [0.5, 1.0, 2.5, 4.0, 5.0, null, NaN, -inf, inf, 3.0, 2.0]`, `k = -2`
(Python: groups `[-1, -1, -2, -2]`, `starts = {g: [-2, -1], lo: [3.0, 1.0]}`).

- Python: `[-2, -1, -1, -1, -1, null, null, -2, -1, -1, -1]`
- Lean:   `[-2, -2, -2, -1, -1, null, null, -2, -1, -1, -2]`

Second input: `reference = [0.2, null, 0.1, NaN, 0.2, 0.4, NaN, 0.3, 0.1, null, 0.9, 0.5]`, same x
plus `[0.1, 0.2, 0.25, 0.9, 0.05]`, `k = -3`: element 0 (x = 0.5) Python -1, Lean -2.
Real data: scenarios a, b, c, reference = first 700 training `pd_logistic`, k = -10: digests differ
in all 6 runs (with and without injected nulls/NaN in the reference); the same runs with
k = 10, 20, 3, 1, 0, 1000 all agree.

The package only calls it with k = 10 (metrics_calculation.py:252-254), so no pipeline output is
affected. Fix options for the orchestrator: add `0 <= k` to `def:proc_rank_apply_groups_precond`
(Python does not raise there, so this narrows the domain and should be recorded), or model the
binary search on a non-sorted array. The unit's claim "lo is sorted" needs the k >= 0 hypothesis
either way.

### P1 — PRECOND — `merge_one_to_one_precond` excludes inputs on which Python does not raise

Second conjunct: a Null-dtype column may only occur in frames of the greatest height. Python pads
a Null-dtype column without error: `merge_one_to_one(DataFrame({'n':[None]}, schema Null), DataFrame({'v':[1.,2.,3.]}))`
gives a 3-row frame with `n` of dtype Null. RULEBOOK §4 describes preconditions as domains and the
cases where Python raises; here it hides a prelude gap (`Pl.Col.append` has no `.null, .null`
case). The implementer declared it (in-body `TODO(port)` and trailer), so this is a recorded
narrowing, not a silent one; it should be carried to the open-items list. Not reachable from the
package's call sites (no Null-dtype column in the merged frames). The allowed Null case (Null
column in a frame of maximal height, `null_dtype_at_max`) agrees with Python.

### N1 — NOTE — `_ratio` is called with Python ints; int / int is not float(a) / float(b) beyond 2^53

sas_compat.py:897-898, 953-954: `_ratio(cd, p)` and `_ratio(cd, q.conc + q.disc)` pass two Python
ints; Python's int true division is correctly rounded from the exact quotient. The Lean unit takes
`(a b : α)`, so a caller can only cast first. With the cast `Pl.ofInt`:

| a, b | Python `_ratio(a, b)` | Lean `_ratio (Pl.ofInt a) (Pl.ofInt b)` |
|---|---|---|
| 9007199254740993, 3 | 3002399751580331.0 | 3002399751580330.5 |
| 9007199254740993, 9007199254740995 | 0.9999999999999998 | 0.9999999999999996 |
| 12345678901234567, 76543210987654321 | 0.16129031878772115 | 0.16129031878772118 |
| 5, 9007199254740993 | 5.551115123125782e-16 | 5.551115123125783e-16 |
| 10^30, 10^29 + 1 | 10.0 | 10.000000000000002 |

(also the negated first row). In every case the Lean equals Python's `float(a) / float(b)`, and all
integer pairs below 2^53 agree (7/2, -7/2, 10/4, 1/0, 0/0, ...). This is inside the recorded limit
"integers beyond 2^53" (RULEBOOK §6) and concerns pair counts above 9e15, but it is a property of
this unit's signature that the callers' reviewers (`def:roc_association`, `def:association_table`)
should know. The unit itself, on floats, is exact: 27/27 including `b = ±0.0` (None), NaN divisor
(NaN, not None), inf/inf, overflow to inf (Python float `/` does not raise), subnormals, -0.0 results.

### N2 — NOTE — `proc_rank_apply_groups`: cases where Python raises are covered

- reference all null or empty: Python `IndexError` at L631 (`g_arr[0]`); Lean returns all null;
  excluded by the conjunct `∃ t, some t ∈ r`.
- `k = 3 * 2^62` with reference `[1, 2, 3, 4]`: Python `InvalidOperationError` (f64 → i64) inside
  `proc_rank_groups`; Lean returns 2.77e18 … 1.1e19; excluded through `proc_rank_groups_precond`.

### N3 — NOTE — `merge_one_to_one` Lean frames with a repeated column name

`merge_one_to_one_precond` does not say that the names inside one frame are distinct. A polars
DataFrame cannot have duplicates, so no Python input corresponds; mentioned only because the
equivalence team will quantify over Lean frames.

## Standing questions

A. Behaviour: one difference (D1). Everything else agrees on every input tried, including the
   null / NaN / tie / empty / zero-divisor cases and the rows where Python raises (N2).
B. Rulebook: no deviation found in the four statements. Header line and trailer present (§4);
   `b == 0` uses `Pl.ofInt 0` with `RealLike.eqb` (§2.2); `(t * Pl.ofInt k) / Pl.ofInt (n + 1)` keeps
   the source grouping (§2.2); R-NULLNAN and R-F2I applied and marked `TODO(port): F2I`; the
   un-ordered `group_by` is followed by a sort on a distinct key and says so (§2.3); `min` inside
   `groupByAgg` is on a Float64 column (§2.3 restriction respected); no local re-implementation of
   a polars / numpy behaviour. P1 is the one place where a precondition is used for something other
   than a Python raise, and it is declared.
C. Docstrings: I found nothing that exists only in a docstring. `merge_one_to_one` follows the dict
   loop (overwrite in place = `setCol`, padding from L251-252). `proc_rank_groups` follows L613-616
   (the docstring formula happens to be the same expression). In `proc_rank_apply_groups` the body
   follows L624-633 line by line, but the sentence "lo is sorted (group starts increase with the
   group number)" is the docstring's picture of the function ("highest group whose start is <= x"),
   not something the code guarantees; it is exactly where D1 comes from. For k < 0 the Lean matches
   neither the code nor the docstring.
D. Parameters: none of the four units has an explicit §3 parameter and none is needed; nothing in
   scope is hidden behind one.
