## Findings

### PRECOND-1 (minor): `_pairs_precond` excludes inputs on which Python runs fine
`def:_pairs_precond` (inherited by the other two) requires each Series to be `.f64`, `.int`,
`.bool` or `.null`. Python (sc:848, `cast(pl.Float64)`) also accepts:
- a String Series of numbers: `association_table(pl.Series(["1","0","1"]), pl.Series([.1,.2,.3]))`
  returns `AssociationTable(50.0, 50.0, 0.0, pairs=2, 0.0, 0.0, 0.0, c=0.5)`. The Lean on
  `Pl.Col.str [some "1", some "0", some "1"]` returns `conc, disc, tied, n1, n0 = 0, 0, 0, 0, 0`
  (`Col.asF64` of a `.str` column is `[]`).
- a Date Series as score: Python returns the same table (the cast gives day numbers); the Lean has
  `.cell` → `[]`.
The exclusion is what makes the unit correct, and the precondition's comment says a String or Date
column is "outside the model". No in-scope caller passes such a column (inventory rows 750-751:
Float64 at every call site). It is still a strict over-restriction: the precondition is sufficient
but not necessary. Decision for the orchestrator: accept as a recorded limit of the model, or note
it in the inventory row sc:848 `[CAST]`, whose text ("identity") does not mention it.

Necessity of the rest, checked: a length mismatch raises `ShapeError` for 2 vs 3, 1 vs 3, 3 vs 1 and
0 vs 3 (no broadcast of a length-1 Series), and there the Lean would silently truncate
(`List.zip`: y of length 2 with a score of length 3 gives `n1 = 1, n0 = 1, disc = 1`). So
`y.len = score.len` is necessary. Sufficiency: no input allowed by the three preconditions made
Python raise or warn (`edge.py`: empty, dtype Null, all NaN, constant scores, under
`warnings.simplefilter("error")`).

### NOTE-1: the `sqrt` conjunct of `roc_association_precond` excludes nothing in IEEE doubles
`¬ (var1 v10 / n1 + var1 v01 / n0 < 0.0)`: in Python the argument is never negative and never NaN
(`v10`, `v01` are finite numbers in [0, 1] whatever the scores are, NaN and inf included, because
they are built from integer counts; `np.var` is a sum of squares over a positive count). 20000
random tie-heavy inputs: minimum argument 0.0. So `math.sqrt` never raises at sc:890 and the
conjunct is vacuous at `Float`. It is required by RULEBOOK §2.2 "Python raises" and is needed for
an abstract `RealLike α`; it is stated on exactly the expression the body evaluates (same `elems`,
same order). Correct, not a finding against the unit. A consumer of the precondition has to prove
it for an abstract `α`.

### NOTE-2: unreachable `.d2` branch of `elems` (roc_association and its precondition)
`| .d2 rows => rows.flatten` states that `np.var` of a 2-D array equals `Np.var1` of the row-major
flattening. No evidence is cited for it and none is needed: `_pairs` always returns `.d1` (sc:862).
A total match is required by Lean; the branch decides no behaviour.

### NOTE-3: integers beyond 2^53 (recorded limit, RULEBOOK §6)
- `_ratio(cd, p)` etc.: Python `int / int` is the correctly rounded quotient; the Lean is
  `ofInt a / ofInt b`. Equal while both are below 2^53 (inventory row 783). Needs n1 * n0 > 9e15.
- An Int64 score column beyond 2^53 is allowed by the precondition. Python rounds in the cast
  (`[2^53, 2^53+1, 2^53+2, 5]` with y `[1,0,1,0]`: conc 3, disc 0, tied 1, v10 `[0.75, 1.0]`).
  The Lean at `Float` gives the same (`[3, 0, 1, 2, 2]`, v10 bits 4604930618986332160,
  4607182418800017408). At an exact number type the cast would not round. Covered by the
  recorded limit; no action.
