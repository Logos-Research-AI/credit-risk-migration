## Findings

### NOTE 1 — an aggregate passed to `sql_*` inside `group_by().agg` (same mechanism as B14, different input)

- Source: sas_compat.py:206-207. Not reached by the package.
- Input: `a = [1.5, null, 2.5, -1.0, 4.0, null]`, `g = [0, 0, 1, 1, 2, 2]`,
  `df.group_by("g", maintain_order=True).agg(o=sql_sum(pl.col("a").sum()))`.
- Python: `o = [1.5, 1.5, 4.0]`.
- Lean (`T.groupByAgg ["g"] [("o", sql_sum (W (c "a").sum))]`): `o = [3.0, 4.0, null]`.
- Cause: the prelude's `count` and `sum` index the already aggregated 3-value column with frame row
  indices. B14 records this for a literal operand only.

### NOTE 2 — Boolean input of `sql_sum`: dtype differs

- Source: sas_compat.py:207. Not reached by the package (flags go through `flag`, which casts to Int64).
- Input: `t = [true, false, null, true, true, false]`, `df.select(o=sql_sum(pl.col("t")))`.
- Python: UInt32 `[3]`; inside `agg` by `g`: UInt32 `[1, 1, 1]`.
- Lean: Float64 `[3.0]`; inside `agg`: Float64 `[1.0, 1.0, 1.0]`. Values agree, the kind does not.
- `sql_mean` of the same column matches (Float64 on both sides). `sql_min`/`sql_max` of a Boolean
  column return Boolean in Python (`[False]`, `[True]`); by reading, the prelude's `aggF` returns
  Float64. I did not evaluate that pair in Lean.
- B14 names the Int64 input of `sql_min`/`sql_max` only; the prelude header does not list `sum` among
  the Float64-only functions.

### NOTE 3 — a String column in `div`, `sas_sum`, `sas_exp`: Python computes, Lean returns an empty column

- Source: sas_compat.py:143, :151, :174 (`.cast(pl.Float64)`). Not reached by the package.
- Input: `s = ["1.5", "2"]` (String).
- Python: `div(pl.col("s"), 2)` = `[0.75, 1.0]`; `sas_sum(pl.col("s"), 2)` = `[3.5, 4.0]`;
  `sas_exp(pl.col("s"))` = `[4.4816890703380645, 7.38905609893065]`.
- Lean: all three are a Float64 column of length 0 (`Col.asF64` of a `.str` column is `[]`).
- B12 says String operands raise. For these three helpers they do not: the cast parses the text. The
  dtype requirement that B12 moves to the `run` steps therefore has to exclude String operands here
  explicitly, with the comment B3 asks for (an input excluded although Python does not raise).

### NOTE 4 — `sas_log(pl.lit(None))`: Python raises, Lean returns a null

- Source: sas_compat.py:169.
- Python: `InvalidOperationError: log operation not supported for dtype null`.
- Lean (`T.select [("o", sas_log (W Pl.litNull))]`): one Float64 null.
- Same class as B12 (a dtype on which polars raises, no precondition on the helper). `sas_exp`, `div`
  and `sas_sum` of the same literal do not raise and match Lean (they cast first).

### NOTE 5 — a non-aggregated operand inside `group_by().agg`

- Source: the module docstring (sas_compat.py:10-11) only promises a scalar per group for aggregate
  or literal operands. Not reached by the package.
- Input: frame of NOTE 1 with `b = [2.0, 0.0, null, 4.0, 0.5, null]`.
- Python: `agg(o=div(pl.col("a"), pl.col("b").sum()))` is `List(Float64)`
  `[[0.75, null], [0.625, -0.25], [8.0, null]]`; `agg(o=sas_log(pl.col("a")))` is a list column too.
- Lean: `[0.75, null, 5.0]` (3 values) for the first; a 6-value Float64 column beside a 3-value key
  for the second.
- `Pl.Col` has no list kind, so the shape is outside the model. It is not listed among the recorded
  limits of §6.

### NOTE 6 — comment in `def:sas_sum_precond`

- The comment says `pl.sum_horizontal` of nothing "raises ComputeError when evaluated". It raises when
  the expression is built: `sas_compat.sas_sum()` itself raises `ComputeError: cannot return empty
  fold…` at line 152, before `args[0]` is reached; `pl.all_horizontal([])` raises the same way.
- The precondition `args ≠ []` is correct. `sas_min()` and `sas_max()` raise `IndexError` as their
  comments say.
