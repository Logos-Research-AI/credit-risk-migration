## Method

Lean evaluated with `eval_decl(item_id="def:zz_carrier", decl="zz_carrier")` at `α := Float`.
Each case evaluates, on the same `(y, score)`:

- `_pairs y s`: `conc, disc, tied, n1, n0` and every element of `v10`, `v01` (constructor `.d1`, length, bits);
- `roc_association y s none`: the 7 fields, matched positionally with `⟨a, b, c, d, e, f, g⟩` (so field order is tested, not only names);
- `roc_association y s (some "Mo\"del é 1")`: the frame — number of columns, each name, each column kind, each value;
- `association_table y s`: the 8 fields, matched positionally.

The values are turned into a token stream (float bits, `none` ≠ NaN, signed ints, strings) and
hashed to one 64-bit digest per case on both sides (same mixing as `kit.py` `dg`). 156 distinct
digests among the 254 small cases, so the comparison is not vacuous. The Python side also asserts
`type(...) is int` / `is float` for every field (no numpy scalar leaks out).

Inputs are my own; random data is generated inside Lean with the kit's `gF`/`gI` and mirrored in
Python. Scripts and outputs (session scratchpad, not kept in the repo):

## Findings

1. **RULE (minor) — `def:Z975`, RULEBOOK §4.** The statement has no trailer
   `-- PORT STATUS: confidence=[..] todos=[N]` (§4: "Every statement ... ends with the trailer").
   Its header is `-- sas_compat.py:43`, not `-- credit_risk/sas_compat.py:43`, and the literal is
   written `:= 1.959963984540054`, not `(1.959963984540054 : α)` (§2.2 form). No effect on the
   value: Lean bits 4611505712243081092 = Python bits.

2. **RULE (minor) — `def:_ratio`, RULEBOOK §4.** Trailer `-- PORT STATUS: confidence=high todos=0`,
   while the seven B4 units write `confidence=[high] todos=[0]`. A grep for one form misses the
   other. No effect on behaviour (15/15 `_ratio` cases equal).

3. **NOTE — precondition items carry no trailer.** `def:_pairs_precond`,
   `def:roc_association_precond`, `def:association_table_precond` start with the source line but
   have no `-- PORT STATUS` line. §4 does not say whether a precondition item needs one.

4. **NOTE — the precondition is narrower than Python's domain (sc:848).** A String Series of
   numeric text is accepted by Python: `_pairs(pl.Series(["1", "0"]), pl.Series([0.1, 0.2]))`
   gives n1 = 1, n0 = 1. `_pairs_precond` excludes `.str` (Lean there: `Col.asF64` = `[]`, so
   conc, disc, tied, n1, n0 = 0, 0, 0, 0, 0). The precondition comment says so. Not a defect: the
   Lean claims nothing there. Float32 input (Python accepts it) has no `Pl.Col` kind.

5. **NOTE — unequal lengths (sc:848).** Python raises `ShapeError` for lengths 3/2, 1/3, 3/1, 0/2
   (a length-1 Series is not broadcast). Lean truncates to the shorter column
   (y = [1, 0, 1], s = [0.1, 0.2] gives conc, disc, tied, n1, n0 = 0, 1, 0, 1, 1). Excluded by
   `y.len = score.len` in `_pairs_precond`, which the two other preconditions include. Correct.

6. **NOTE — `drop_nulls` on a frame and `.cast(pl.Float64)` on a Series are not in §2.3.** The
   Lean uses list code and the prelude's `Pl.Col.asF64`, as the inventory rows L848 prescribe
   (status confirmed), without a `-- TODO(port)` marker (§2.3, last paragraph). The behaviour is
   verified here for Float64, Int64, Int32, UInt8, Boolean and Null columns. Suggest adding the
   two rows to §2.3 rather than marking the unit.

7. **NOTE — inventory rows that no longer match the accepted Lean** (the Lean is the one that
   agrees with the rulebook and with Python):
   - L901: "translate the frame-returning form, keep the record as a helper
     `roc_association_stats`". The Lean returns `RocAssociation α ⊕ Pl.Frame α`, as §3 requires.
   - L851, L852: `eqb yy_i 1.0` / `0.0`. The Lean writes `Pl.ofInt 1` / `Pl.ofInt 0` (§2.2, int
     literal where a float is expected). Same value at `Float`.
   - L848 casts: "identity (Float64 at every call site)". The Lean also models Int64, Boolean and
     Null inputs and the precondition admits them; all verified bit for bit.
   - L890: "it is NaN when a score is NaN". It is not: `v10`/`v01` are built from integer counts
     and are never NaN (NaN-score cases give finite `std_err`, equal in Lean and Python).

8. **NOTE — `roc_association_precond`, second conjunct.** `¬ (var/n1 + var/n0 < 0.0)` is stated
   because `math.sqrt` raises on a negative argument (§2.2 "Python raises"). At `Float` it always
   holds (a variance is a sum of squares over a positive count). Correct and not restrictive.

9. **NOTE — known limit, not tested.** `_ratio(cd, p)` is Python int / int (correctly rounded
   from the exact integers); `Pl.ofInt cd / Pl.ofInt p` equals it only while both are below 2^53
   (§6 known limits; inventory L866). It needs about 10^8 rows to matter.
