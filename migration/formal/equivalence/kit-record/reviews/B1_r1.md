## Findings

### F1 — PRECOND: `confusion_metrics_precond` excludes inputs on which Python runs, with a wrong justification

`numeric n` accepts only `.f64` / `.int` for `pd_logistic` and `default_flag`. The comment says
"polars raises when the column is absent or cannot be compared with a number". That is true for a
String column (`ComputeError: cannot compare string with numeric type`, both columns) and for an
absent column (`ColumnNotFoundError`), but not for Boolean or Null-dtype columns:

| Input (threshold 0.5) | Python | Lean |
|---|---|---|
| `pd_logistic=[0.1,0.9,0.7]`, `default_flag=[True,False,None]` (Boolean) | runs; conf_matrix `default_flag` Boolean | identical (3 frames, digest PASS) |
| `pd_logistic=[True,False,None]` (Boolean), `default_flag=[1,0,1]` | runs | identical |
| `pd_logistic` Null dtype `[None,None]`, `default_flag=[1,0]` | runs: metrics `(0.5, 0.5, None, 0.0, None, 1.0)` | identical |
| `pd_logistic=[0.1,0.9]`, `default_flag` Null dtype | runs: all five metrics null | identical |

So the precondition is sufficient (no allowed input on which Python raises was found) but not
necessary, and the exclusion is not justified by the comment. Low impact: the frames reaching this
unit come from `Pl.ofTable` (Float64 / String columns only). Either widen `numeric` to `.bool` and
`.null`, or correct the comment to say the exclusion is a modelling choice.
Reference: reviewer.md question A ("what happens where Python raises: is it in the precondition"),
RULEBOOK §4 Preconditions.

### F2 — PRECOND: `flag` has no precondition and differs from Python on a non-Boolean condition

`sas_compat.py:122-124`. `cond: pl.Expr` is not restricted to Boolean by the code.
Input: frame `i = [1, null, 0, 5]` (Int64), expression `flag(pl.col("i"))`.
- Python: Int64 `[1, 0, 0, 5]` (`fill_null(False)` keeps Int64).
- Lean (`eval_decl`, `fr.select [(flag (Pl.col "i")).pos]`): Float64 `[1.0, 0.0, 0.0, 5.0]`
  (bits 4607182418800017408, 0, 0, 4617315517961601024) — the prelude `Col.fillNull` of `.int` with
  `.bool` falls to the Float64 branch and `castI64` leaves a Float64 column unchanged.
- Also `flag(pl.col("s"))` on a String column raises `InvalidOperationError` in Python; the Lean
  is total.

Every call site in scope passes a Boolean expression, so no result of the pipeline is affected, but
RULEBOOK §4 asks for a precondition "for each unit that needs one … the cases where Python would
raise"; `def:flag_precond` does not exist. Needed: "`cond` evaluates to a Boolean column".
(The Int64 behaviour of `fill_null(False)` is a prelude gap, `def:ExprOrNum` `Col.fillNull`; I did
not touch it.)

### F3 — PRECOND: comparison helpers and `sas_round` have no precondition for the inputs on which Python raises

- `lt(pl.col("s"), 1.0)`, `ge(pl.col("s"), 1)`, `eq(pl.col("s"), 1.0)` with a String column `s`:
  Python raises `ComputeError: cannot compare string with numeric type`. The Lean is total
  (`cmpBin` falls to `asF64`, which is `[]` for a `.str` column, so the result is an empty Boolean
  column). String vs String works in Python (`lt(s, lit("b")) = [True, True, False]`,
  `eq(s, lit("a")) = [True, False, False]`) and is modelled by `cmpBin`'s `.str, .str` case.
- `sas_round(pl.col("s"))`: Python raises `InvalidOperationError` (cast to Float64 fails); the Lean
  returns an empty Float64 column.

No `def:lt_precond`, `def:le_precond`, `def:gt_precond`, `def:ge_precond`, `def:eq_precond`,
`def:sas_round_precond` exist (checked with `get_items`). RULEBOOK §1 "Errors" and §4: where Python
raises, the unit's precondition excludes the case. No call site in scope passes such operands.
