## Findings

### F1 — DEFECT (prelude `groupSum` / `groupMean`, reached through `sql_sum`, `sql_mean`): group key that carries polars' sorted flag

`sas_compat.py:207`, `:213`; RULEBOOK §6 row "`kahan`, `groupSum`, `groupMean`" (not among the
recorded limits). When the `group_by` key column has the sorted flag (the frame was sorted by that
key), polars 2.1.0 builds slice groups and sums each slice with the select-context kernel, not with
the Kahan fold. The prelude always uses Kahan.

Input: frame `g = [0,0,0,1,1,1]` (Int64), `a = [0.1, 0.2, 0.3, 0.7, 0.1, 0.2]`,
`df.sort("g", maintain_order=True).group_by("g", maintain_order=True).agg(s=sql_sum(pl.col("a")), m=sql_mean(pl.col("a")))`
against `(SM.sort ["g"]).groupByAgg ["g"] [("s", sql_sum (X "a")), ("m", sql_mean (X "a"))]`.

| | `s` group 0 | `m` group 0 |
|---|---|---|
| Python | bits 4603579539098121012 (0.6000000000000001) | bits 4596373779694328219 (0.20000000000000004) |
| Lean | bits 4603579539098121011 (0.6) | bits 4596373779694328217 (0.19999999999999998) |

Group 1 agrees (1.0, 0.3333333333333333). The same six rows without the sort (key has no flag)
agree bit for bit (digest 928757443981268982 both sides). On 1000 random rows sorted by the key
(10 groups, and 700 groups) the frames also differ; `sql_min` / `sql_max` are unaffected.

Reach: none of the package's `group_by` sites that aggregate floats has a flagged key
(`metrics_calculation.py:174`, `:317` group on `decile` / `pred_bin`, new Series built by
`proc_rank_groups`; checked `Series.flags` and evaluated the package-shaped cases — frame sorted by
the aggregated column, key unflagged; and sort by key followed by `key + 1` — all identical). So this
is an unrecorded limit of the model, one `df.sort(key)` away from the package's shape. It is a prelude
matter (`def:ExprOrNum` is frozen): record it in §6 or state "the group key has no sorted flag" in
the preconditions of the steps that call `groupByAgg` with a float sum or mean.

### F3 — PRECOND (`def:sas_sum_precond`; RULEBOOK §3 `full`): 9 or more operands on a 2- or 3-thread pool

`sas_compat.py:152`. With `POLARS_MAX_THREADS=2` or `3` and N ≥ 9 operands, `pl.sum_horizontal`
returns a value that neither `full = true` nor `full = false` gives, and it varies from run to run.

Input: one row, nine Float64 columns `[7.9, 6.5, 4.0, 8.3, 1.0, 6.3, 3.9, 5.3, 8.4]`,
`sas_sum(c0, …, c8)`.

| | Result bits |
|---|---|
| Lean `sas_sum true` | 4632458871708634317 |
| Lean `sas_sum false` | 4632458871708634316 |
| Python, 1 thread (200 runs) | …316 × 200 |
| Python, 2 threads (200 runs) | …318 × 156, …317 × 44 |
| Python, 3 threads (200 runs) | …317 × 165, …318 × 35 |
| Python, 4 and 12 threads (200 runs each) | …317 × 200 |

…318 is `((a+b)+(c+d)) + ((e+f)+((g+h)+i))`: the right half is split once more, then folded. On 4000
random rows: N = 1…8 match `full=true` (≥ 2 threads) or `full=false` (1 thread) in 30/30 runs at
every pool size; N = 9…12 at 2–3 threads match neither in most runs. The precondition says only
`args ≠ []`. Not reached by the package (at most 5 operands: `feature_engineering.py:185`,
`predict.py:191`). `sas_min` / `sas_max` are not affected in value (min/max are associative).
